# 00. 리서치 개요 · 전제 · 제약

## 1. 이 사이트가 동시에 풀어야 하는 두 가지 문제

| | B2C (일반 소비자) | B2B (해외 바이어/딜러) |
|---|---|---|
| 목적 | "퍼피아 = 소프트하네스의 전문 브랜드"를 3초 안에 각인 | 카탈로그 열람 → 견적/발주 → 문의 대응까지 자기 완결 |
| 지표 | 체류시간, 스크롤 깊이, 제품 상세 도달률, 리테일러 이동률 | 바이어 가입 승인 수, 포털 재방문율, 문의→견적 전환 |
| UX 성격 | 화보·모션·3D 중심의 "쇼룸" | 밀도 높은 표·검색·다운로드 중심의 "업무 도구" |

**핵심 원칙: 두 영역은 시각 언어를 공유하되 UX는 완전히 분리한다.**
쇼룸에 표를 넣거나 바이어 포털에 3D를 넣으면 양쪽 다 망가진다. 같은 타이포·같은 컬러·같은 로고를 쓰되, `/` 는 몰입형, `/partners` 는 도구형으로 간다. (Arc'teryx, Ruffwear 등 B2B 병행 브랜드가 모두 이 구조다.)

## 2. 브랜드 포지셔닝 전제

- 사용자가 세운 가설: **"애플의 아이폰 = 퍼피아의 소프트하네스"**
- 이 가설이 성립하려면 사이트가 증명해야 하는 것은 "예쁘다"가 아니라 **"이 카테고리를 우리가 정의했다"** 다.
- 애플이 아이폰 페이지에서 실제로 하는 것은 자랑이 아니라 **해부(anatomy)** 다. 칩, 카메라, 소재를 층층이 분해해 보여준다. 퍼피아도 동일하게 가야 한다: 원단 → 패턴 → 봉제 → 체형 적합성.
- 즉 **"소프트하네스 시리즈" 전용 페이지가 홈 다음으로 중요한 페이지**가 되어야 하며, 신상은 그 아래 계층에 놓인다.

## 3. 카페24 웹호스팅 제약 (반드시 설계 전 반영)

리서치로 확인된 사실:

| 항목 | 확인된 내용 | 설계 영향 |
|---|---|---|
| PHP / DB | 뉴아우토반 호스팅 기준 PHP 8.4~7.4, MariaDB 10.x 지원 | 바이어 포털 백엔드는 **PHP + MariaDB**로 간다 |
| Node.js 호스팅 | 최대 **Node 14**까지만 지원, **SSL 인증서 설치 미지원**, FTP 불가(git 배포만) | **Next.js/Nuxt SSR 서버를 카페24에 올리지 않는다.** Node 14는 이미 EOL이고 SSL 미지원은 글로벌 사이트에서 치명적 |
| 트래픽 | 뉴아우토반/자이언트플러스 기준 월 1.2TB 기본, 초과 시 165원/GB 종량 (차단은 되지 않음) | 3D·영상 자산을 카페24에서 직접 서빙하면 비용이 튄다 → **CDN 필수** |
| SSH | SSH2 지원 (PuTTY 등) | 배포 자동화 가능 |
| 스토리지 | FullSSD | 정적 자산 서빙 자체는 무난 |

**결론적 스택 권고**

```
[사용자]
   ↓
Cloudflare (무료 플랜으로도 충분) — SSL, 글로벌 CDN, 캐싱, 이미지/영상 대역폭 흡수
   ↓
카페24 웹호스팅 (PHP 8.x + MariaDB 10.x)
   ├─ /            → 정적 빌드 산출물 (HTML/CSS/JS) 업로드   ※ Astro 또는 Vite SSG로 로컬/CI 빌드 후 FTP·SSH 업로드
   ├─ /api/*.php   → 문의 티켓, 바이어 인증, 주문서, 자산 다운로드 로그
   └─ /partners/   → 세션 기반 로그인 영역 (PHP)
   
[별도] 3D 모델(.glb)·동영상·고해상 화보 → Cloudflare R2 / S3 등 오브젝트 스토리지 + CDN
```

- 프론트엔드는 **빌드 결과물만 올리는 정적 사이트**로 간다. 카페24는 Node 런타임을 실행하지 않고 파일만 서빙한다 → Node 14 문제와 SSL 문제를 동시에 회피.
- 동적 기능(로그인, 주문, 문의)만 PHP로 처리한다. 3D·모션은 전부 클라이언트 사이드라 서버 성능과 무관하다.
- 만약 향후 SSR/ISR이 꼭 필요해지면 카페24를 고집하지 말고 프론트만 Vercel/Cloudflare Pages로 분리하고 카페24는 API·DB 역할만 남기는 하이브리드가 현실적이다.

## 4. 성능 예산 (3D를 쓰기로 한 이상 먼저 정해야 함)

리서치에서 반복적으로 확인된 원칙: *"블로킹하는 WebGL 씬은 Core Web Vitals를 망친다. 다만 lazy init + DPR 제한 + 압축 자산 + 폴백이 있으면 3D 사이트도 좋은 LCP/INP를 유지한다."*

| 항목 | 예산 |
|---|---|
| LCP (모바일 4G) | ≤ 2.5s — **히어로의 LCP 요소는 3D가 아니라 정적 이미지/텍스트** |
| 첫 화면 JS | ≤ 200KB (gzip). Three.js 번들은 지연 로드 |
| .glb 모델 1개 | ≤ 3MB (Draco 지오메트리 압축 + KTX2/Basis 텍스처) |
| 모바일 | DPR 상한 2, 그림자 해상도 축소, WebGL 미지원 기기엔 **WebP 스틸 폴백** |
| 접근성 | `prefers-reduced-motion` 존중, 사운드 기본 OFF + 토글, 자동재생 영상은 muted+playsinline |
| SEO | 3D 씬 뒤에 **실제 HTML 텍스트**가 존재해야 한다. 캔버스만 있는 페이지는 색인되지 않는다 |

이 예산은 "나중에 최적화"가 아니라 **디자인 결정의 제약**으로 먼저 박아두어야 한다.
